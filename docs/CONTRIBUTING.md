# Регламент командной разработки (Team Development & Contributing Guide)

> **Команда проекта «Тренажер энергоблока ВВЭР-1200»**  
> Данный регламент предназначен для внутреннего использования командой разработчиков. В проекте нет сторонних контрибьюторов — документ определяет внутренние договоренности, зоны ответственности, правила ведения веток, синхронизацию протоколов и юридический статус проекта.

## 👥 1. Обращение к команде и зоны ответственности

 Чтобы разработка шла слаженно, не ломала сетевой протокол и не создавала конфликтов слияния, каждый участник команды придерживается своей области:

| Направление | Ответственность | Ключевые файлы |
|---|---|---|
| **Сервер симуляции (Physics Engine)** | Математическая модель (кинетика, 4 петли, КД, ПГ, турбина), расчет шага 50 мс, WebSocket-стриминг 20 Гц, валидационные тесты физики. | `/VVER_1200_Sim_Server/src/*`<br/>`TEST_DASHBOARD.html` |
| **Веб-интерфейс (Frontend & БЩУ)** | Интерактивная мнемосхема энергоблока (`PlantMimic`), светосигнальные табло БЩУ, пульт инструктора, верстка, эргономика SCADA. | `/VVER-1200/power-unit-operator-simulator/src/*` |
| **Интеграция и протоколы (Связка)** | Служба `simulatorService`, согласование названий полей в JSON-пакетах, словарь команд, уставки защит. | `simulatorService.js`<br/>`DATA_DICTIONARY_VVER1200.txt`<br/>`docs/API_AND_PROTOCOLS.md` |

> ⚠️ **Главное правило**: При любых изменениях полей в телеметрии или параметров команд **в первую очередь** обновляется спецификация [`docs/API_AND_PROTOCOLS.md`](./API_AND_PROTOCOLS.md) и уведомляется второй разработчик, чтобы интерфейс не терял реактивность.

## 🌿 3. Командный рабочий процесс в Git

### 3.1. Правило веток
- Ветка **`main`** всегда находится в стабильном, рабочем состоянии (все тесты проходят, интерфейс открывается без ошибок).
- Прямые коммиты в `main` запрещены. Вся разработка ведется в тематических ветках:
  - `feature/имя-фичи` — разработка нового узла (например, `feature/pressurizer-spray`);
  - `fix/имя-бага` — исправление бага в термогидравлике или верстке;
  - `docs/тема` — правки технической документации.

### 3.2. Стандарт коммитов (Conventional Commits)
Для прозрачной истории используем понятные префиксы:
```bash
git commit -m "feat(mimic): добавить анимацию циркуляции теплоносителя в петлях"
git commit -m "fix(physics): скорректировать Допплер-коэффициент топлива при разгоне"
git commit -m "test(engine): добавить тест удержания уровня в парогенераторах"
git commit -m "docs(api): задокументировать команду сброса стопорных клапанов турбины"
```

### 3.3. Локальные файлы и переменные окружения
- Файлы `.env` с локальными портами и путями **никогда не коммитятся** (они внесены в `.gitignore`).
- Если вы добавили новую переменную окружения, обязательно добавьте ее с описанием в `.env.example`.

## 🧪 4. Чеклист перед слиянием (Pre-Merge Checklist)

Перед слиянием своей ветки в `main` каждый разработчик обязан:

1. **Для бэкенда / физического ядра**:
   ```bash
   cd VVER_1200_Sim_Server
   npm run simulation:test
   ```
   > Все 16 автоматических валидационных тестов (кинетика, баланс массы и энергии, выбег ГЦН, сброс АЗ-1) должны возвращать `[PASS]`.

2. **Для фронтенда**:
   ```bash
   cd VVER-1200/power-unit-operator-simulator
   npm run build
   ```
   > Сборка React должна проходить успешно без критических предупреждений и ошибок сборщика.

3. **Сетевой тест**:
   Запустить локально сервер (`npm start` в сервере) и клиент (`npm start` в клиенте) и убедиться, что индикатор в шапке показывает `● СЕТЬ: ОНЛАЙН (20 Гц)` и стрелки приборов реагируют на команды.
