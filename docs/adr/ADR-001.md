# ADR-001: Выбор технологического стека и декларация инструментального контура

> **Статус:** Принято (Accepted)  
> **Дата:** Сентябрь 2026  
> **Авторы:** Команда проекта «Тренажер ВВЭР-1200» (Евгений Миусский, Степачева Полина, Яриш Арина, Анна Сморгун, Журавель Полина)  
> **Контекст решения:** Контрольная точка КТ-1 · Дисциплины МДК.01.04 и МДК.03.02  

---

## 1. Контекст и постановка проблемы

Перед командой стояла задача разработки учебно-тренировочного комплекса энергоблока ВВЭР-1200, состоящего из:
1. Вычислительного математического ядра реального времени (численное решение системы дифференциальных уравнений нейтронной физики и термогидравлики с фиксированным шагом квантования времени $\Delta t \le 0.05$ с / 20 Гц);
2. Высокоотзывчивого графического веб-интерфейса оператора блочного щита управления (БЩУ) и инструктора;
3. Сетевого транспорта с минимальной задержкой (< 15 мс) для трансляции телеметрии.

### Ограничения продукта и команды:
* Необходимость запуска тренажера на обычных персональных компьютерах и в браузерах учебных аудиторий без установки специализированных проприетарных SCADA-пакетов;
* Опыт команды в стеке веб-технологий (TypeScript / JavaScript / Node.js / React);
* Возможность автономного тестирования физического ядра в headless-режиме (без запуска графической оболочки).

## 2. Рассмотренные альтернативы

| Вариант стека | Достоинства | Недостатки / Причины отклонения |
|---|---|---|
| **Вариант А: C++ / Qt** | Максимальная скорость вычислений ОДУ. | Высокая сложность кроссплатформенной дистрибуции на студенческих ПК; сложности веб-доступа; избыточная трудоемкость верстки SCADA-интерфейсов по сравнению с веб-технологиями. |
| **Вариант Б: Python / FastAPI + React** | Богатая экосистема научных библиотек (NumPy, SciPy). | Ограничения GIL (Global Interpreter Lock) при высокочастотной потоковой передаче (20 Гц) по WebSocket; неоптимальная производительность циклов ОДУ на чистом Python без компилируемых C-расширений. |
| **Вариант В (ВЫБРАН): Node.js + TypeScript (Backend) и React (Frontend)** | Строгая типизация параметров физики, единый язык fullstack-разработки, неблокирующий event loop таймера 20 Гц, нативная работа с WebSocket, компонентная верстка БЩУ. | Требует контроля нагрузки на сборщик мусора V8 и троттлинга частоты обновлений в React. Решено архитектурно. |

---

## 3. Принятое решение

Выбран стек **Node.js 20 + TypeScript 5.8** для вычислительного сервера и **React 19 + Vanilla CSS** для клиентского интерфейса БЩУ.

### Инженерное обоснование:
1. **Строгая статическая типизация (`TypeScript`):**  
   Физическая модель ВВЭР-1200 оперирует более чем 80 связанными величинами (мощности, расходы, реактивности, энтальпии, давления). Строгие интерфейсы (`ControlInputs`, `ReactorInternalState`, `DerivedTelemetry`) исключают ошибки размерностей и обращение к неопределенным полям еще на этапе компиляции.
2. **Неблокирующая модель исполнения (`Node.js Event Loop`):**  
   Таймер физического шага $50$ мс (`setInterval`) и асинхронный broadcast через библиотеку `ws` обеспечивают стабильную частоту дискретизации без деградации при подключении нескольких клиентов.
3. **Компонентная модель (`React 18/19`):**  
   Позволяет изолировать независимые технологические узлы (мнемосхема, табло БЩУ, карточки приборов) с локальным ререндерингом без торможения всего интерфейса.

## 4. Декларация инструментального контура (7 позиций КТП)

В соответствии с требованиями КТП задекларирован полный контур инструментов разработки с маршрутом их подключения в течение семестра:

| № | Позиция КТП | Выбранный инструмент | Текущий статус на КТ-1 | Маршрут подключения в семестре |
|---|---|---|:---:|---|
| **1** | **Подготовка окружения и сборка** | `npm`, TypeScript Compiler (`tsc`), `react-scripts build` | ✅ **Работает** | Сборка бэкенда (`npm run build`) и фронтенда (`npm run build`). Настроена компиляция в `dist/` и `build/`. |
| **2** | **Управление зависимостями** | `npm` (Node Package Manager), файлы `package-lock.json` | ✅ **Работает** | Строгая фиксация хэшей зависимостей в `package-lock.json`. Запрет плавающих версий. Воспроизводимая установка через `npm ci`. |
| **3** | **Автоматические тесты** | Validation Runner (`tsx src/validation/run-tests.ts`), `Jest` / React Testing Library | ✅ **Работает** | Запуск 16 автоматических валидационных тестов физики (`npm run simulation:test`) и базовых тестов UI (`npm test`). На КТ-2 — расширение unit-тестами теплообмена. |
| **4** | **Статический анализ** | TypeScript Strict Type Checking (`tsc --noEmit`), ESLint | ⚠️ **Базовый** | Проверка типов встроена в сборку. На КТ-2 — добавление отдельного скрипта `npm run lint` с единым стилем кода. |
| **5** | **Отладка и диагностика выполнения** | Встроенный инспектор V8 (`node --inspect`), Chrome DevTools, структурированный лог | ✅ **Работает** | Сервер выводит структурированные логи старта, режимов и ошибок. Подключение отладчика через порт 9229. |
| **6** | **Профилирование** | Node.js V8 Profiler (`--prof`), Chrome DevTools Performance Profiler, `clinic.js` | 🟡 **Маршрут** | Запланировано к КТ-2 для замера времени вычисления одного шага математической модели (target: $t_{\text{step}} < 5$ мс при бюджете 50 мс). |
| **7** | **Автоматические проверки в CI** | GitHub Actions Workflow (`.github/workflows/ci.yml`) | ✅ **Подключен** | Автоматический запуск тестов физики и сборки при каждом push и pull request в ветку `main`. |

## 5. Последствия решения (Consequences)

* **Положительные:**
  - Высокая скорость разработки за счет использования единого языка TypeScript на клиенте и сервере;
  - Исключение рассинхронизации структур данных телеметрии благодаря единому словарю типов;
  - Возможность легкого развертывания как локально, так и в облаке или контейнере Docker.
* **Компенсируемые риски:**
  - Нагрузка на React Fiber при частоте 20 Гц компенсирована внедрением троттлинга на уровне 70 мс (~14 кадров/с) в `simulatorService.js`.
